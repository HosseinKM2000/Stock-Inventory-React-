## End-to-end paths

### PWA update and local migration path

Each production build stamps a unique build ID into both the application and service worker. Installation creates a build-specific app-asset cache and fetches the shell plus every Vite manifest asset as one required set. A partial download makes the installing worker redundant; it never replaces the current controller. A completely installed worker remains waiting until a client explicitly accepts it. The update UI distinguishes checking, ready, deferred, applying, and failed states and retains the current working build on check/install failure.

Activation first rejects unsaved forms or active React Query writes, then acquires `tanzim-app-update-activation -> tanzim-outbox-sync -> tanzim-local-mutations:<actor>` with non-waiting Web Lock requests. This matches the existing outbox-before-local-mutation boundary and does not hold a lock across user confirmation or network download. Recovery sessions in `preparing`, `media_staged`, or `database_committed` defer activation; durable outbox/media-transfer entries, recovery review evidence, and unknown outcomes do not. Those records retain their operation/transfer IDs, payloads, attempt state, actor/store and policy context for the new build to resume or expose. A failed recovery-state read also defers rather than reloading blindly.

The service worker never clears IndexedDB, OPFS, session state, recovery evidence, or an outbox. Old build caches remain while any open window reports an older build ID, allowing that document to request its old hashed lazy chunks after the new worker activates. The active worker uses its own cache for offline navigation, while hash-specific static lookup can still find retained prior assets. Obsolete `tanzim-app-*` caches are removed only after every currently open client reports the active build; an abandoned prior cache may therefore remain conservatively until a later client message. Deployment must retain at least the prior supported immutable asset generation until open old tabs have aged out; the worker alone cannot compensate if the server deletes an uncached old chunk.

Actual Dexie rehearsals cover direct `v10 -> v13`, `v12 -> v13`, a transactionally failed upgrade, and an upgrade blocked by an old connection. Products, image references, attempted operation identity/payload/context, recovery checkpoint/imported evidence, and the new transfer table survive. A failed upgrade leaves the previous committed schema/data recoverable; a blocked tab receives a close-other-tabs/retry message. Once an upgrade commits, an older application is not assumed able to reopen the advanced database.

Release order is: verify database and durable-media backups/restores; rehearse PostgreSQL through `20261104_0014` and verify the media mount; stop incompatible backend workers; apply/verify the server schema; start only compatible backend workers; publish all new immutable assets and shell metadata; publish the new service worker last. Before any schema/client migration, rollback may restore the previous complete artifacts while retaining their immutable assets. After PostgreSQL or local schema advancement, rollback is not an arbitrary old-client launch: use a reviewed downgrade/preflight where supported or forward-fix with preserved data. The repository still has no automated deployment/rollback, cache-age policy, cross-browser service-worker matrix, or production backup drill.

### Solo mutation path

1. Inventory form/service validates input and calls a local repository.
2. `local-mutation-storage.ts` commits the projection and outbox record in one Dexie transaction; UI success follows that local commit.
3. `queue.service.enqueue` consolidates pending work and schedules sync.
4. `sync-service.ts` claims due work, `sync.api.ts` sends a batch, and `backend/app/routers/sync.py` resolves membership, entitlement, permission, resource scope, version, and operation id.
5. Accepted state/change cursor is returned and reconciled into the local projection; conflicts/fatal rejections remain local recovery entries.

Operational reads, writes, bulk paths, file authorization, categories, labels, custom products, transactions, and sync pull use the authenticated store boundary. `user_id` remains on transitional tables as the original owner compatibility value; `actor_user_id` and membership IDs retain server-derived attribution. PostgreSQL relation constraints reject cross-store category, inventory, barcode, movement, and transaction references; a migration trigger protects the legacy inventory-label join shape.

This local-first path is active only for the owner while the server-resolved store mode is `solo`. Personnel creation or reactivation requires `team`.

### Team mutation path

`Store.operating_mode` and monotonic `policy_version` are server-owned. `queue.service.ts` captures both before dispatch; after an attempt they are immutable command semantics. `team-command.service.ts` persists a new command before dispatch, requires online connectivity, and serializes predecessor inspection and dispatch with an actor/store/resource Web Lock. It waits for sync resolution and never updates the projection optimistically. Existing entity sync handlers persist only accepted server records. An unknown response keeps the same operation ID for restart/retry; conflict and rejection remain recovery evidence. Reconciliation captures the actor/store before network I/O and aborts with `SYNC_ACCOUNT_CHANGED` before projection or acknowledgement writes if the authenticated partition changes.

`sync.py` locks the store row while validating policy, serializing acceptance with activation. Exact historical replay is resolved by server-derived store/actor, operation ID, and fingerprint before current-policy validation, so a committed pre-transition request returns its recorded result without another domain effect. A new request with missing/stale policy context is stored as a non-retrying rejection. Direct legacy operational routes reject team writes, so an older client cannot bypass the idempotent command path.

Owner activation uses a durable browser-local transition ID and expected policy version until the authoritative result is confirmed. The browser requires Web Locks, sets a maintenance marker checked by local mutation transactions, refuses unfinished recovery review, drains sync, and rechecks the scoped outbox/recovery journal before the short atomic server transition. Activation and restore share the deadlock-free `outbox -> local mutation` lock order; the final drain runs under the already-held outbox lock. A lost response reuses the same transition ID, and simultaneous activation requests converge on the one-way Team state. It does not hold a database transaction while client work drains. There is no ordinary team offline-draft implementation.

### Synchronization and retry

The verified SYNC-001 root cause had two cooperating parts: client compaction could replace the payload of a `retryable_error` operation while retaining its already-transmitted id, and acknowledgement reconciliation could write the older server record before accounting for a newer successor. Server deduplication then correctly returned A's recorded result, but the client could misapply it to the mutated local snapshot and lose edit B.

`queueStorage.claim` durably records an attempt before dispatch and leases the operation. Only never-attempted pending absolute mutations may compact; after any possible transmission the operation identity and payload are frozen, and a later edit receives a new operation id. Additive inventory movements never compact. Queue selection preserves order per logical resource while allowing independent resources to progress. An accepted predecessor may update only a `pending`/`never` successor's base version to the predecessor's accepted version, without changing its identity or business intent. The server still compares that base with its current version, so an intervening update from another device produces a conflict rather than being overwritten.

Server `SyncOperation` stores a canonical SHA-256 request fingerprint with the result. An exact replay returns the recorded result; reuse of an operation id with different semantics is a terminal `OPERATION_PAYLOAD_MISMATCH`. Historical rows without a fingerprint are rejected conservatively as `OPERATION_PAYLOAD_UNVERIFIED`. PostgreSQL advisory serialization and one transaction cover duplicate detection, domain application, and result persistence for a given actor/operation id.

Dexie version 11 marks pre-existing queue entries with unknown attempt history as `uncertain`, so they cannot be compacted after upgrade. This preserves their current payload and backup compatibility, but it cannot reconstruct an older payload that a previous application version had already overwritten before the migration.

### Media

Forms re-encode accepted images as bounded WebP, stripping source metadata, and store the result in OPFS. Dexie v13 keeps a store/actor/product-bound transfer identity, SHA-256, attempt state, backoff, and terminal/retryable outcome independently from the product outbox. The job is durably marked attempted before dispatch; after any possible transmission its identity and content are immutable. Exact retry converges on one `MediaAsset`, while reuse with another fingerprint fails terminally. Media work is bounded and a failed asset does not stop unrelated operational resources.

The backend validates the claimed digest, actual WebP container/dimensions/pixel bound, byte limit, and generated content-addressed key, then fsyncs and atomically replaces the durable file before recording availability. Staged assets are private: a read is authorized only when an active product in the authenticated store references the asset. In Team mode, the upload never publishes the association; the versioned sync command does so under the standard acceptance checks. Replacement and deletion leave old bytes unreferenced rather than risking destructive garbage collection. Preview and detail are separate protected endpoints but currently deliver the same optimized WebP derivative, so a separately resized thumbnail remains an efficiency improvement rather than a correctness dependency.

The sync settings page reports local/server/missing byte coverage and offers `دریافت تصاویر برای استفاده آفلاین`. Recovery downloads with bounded concurrency, validates response type/hash/version, rechecks the authenticated partition and current product association after I/O, checks available browser quota, and only then commits the OPFS reference. A replaced or deleted product, late account/store response, corrupt byte stream, or quota failure cannot produce false local completion. Backups include available local bytes and explicitly list server-only paths as unavailable evidence; they do not claim those bytes are inside the backup.

### Atomic invoices

An invoice post is one immutable sync command, not a group of independently retryable line movements. Duplicate products are consolidated only when unit, package size, and transaction price agree; otherwise the request is rejected before stock checks. Prices are explicit non-negative integer toman values, so zero is distinct from missing. Package quantity is converted to base stock while the entered price remains the package transaction price. Product sale/purchase prices are never rewritten by an invoice.

Server acceptance locks the referenced inventory rows in stable ID order and commits the store/actor-attributed invoice, immutable line snapshots, movements, stock versions, activity, and `SyncOperation` result in one transaction. Exact request replay returns the stored result. Full cancellation locks the original invoice and current product rows, creates compensating movements, and retains the original snapshots; a purchase reversal is refused when later consumption leaves insufficient stock. History reads are store-scoped and redact purchase totals/line prices without `products.purchase_price.view`.

Dexie v14 adds the person/store-partitioned invoice projection, and backup schema 5 carries invoice snapshots plus the existing exact pending command evidence. Solo posts projection, stock effect, and command atomically; rejection compensation applies only when the current quantity still equals the recorded optimistic after-value. Team persists the command before dispatch but publishes neither invoice nor stock until acceptance. Alembic `20261104_0015` adds `invoices`, `invoice_lines`, and store-consistent movement references. Pre-06A workers and pre-v14 clients do not understand this contract, so deployment requires the existing stopped-worker/current-copy rehearsal and a coordinated compatible frontend/backend release. No existing plan is enabled by the migration.

TZ-V1-06B keeps invoice selection and presentation outside the mutation boundary. Camera and hardware input resolve an active barcode only through the authenticated person/store partition and the current barcode capability/permission; the selected product then enters the same manual draft path. A repeated result focuses the existing row without changing quantity, unit, or price, and account changes invalidate pending lookup/camera work. Lookup creates no movement, invoice, queue entry, or stock effect.

PDF, print, and native file share are derived only from the immutable stored invoice line snapshots. Accepted/cancelled invoices are eligible; a Solo pending invoice is explicitly labelled local-only, while rejected/conflicted/cancel-pending and Team-unknown work cannot be presented as final. Purchase/sale price permissions are checked again at output time, and the person/store partition is revalidated after asynchronous PDF generation. The browser-rasterized A4 PDF embeds the already-cached local Persian font rendering, repeats table headers over page breaks, and marks every cancelled page. Sharing sends only the generated file when the platform supports file sharing; it creates no public URL. These output actions never call invoice mutation or synchronization services and add no schema or backend dependency.

### Operational dashboard and invoice reports

TZ-V1-07 derives operational product counts and their detail lists from one eligibility/filter vocabulary. Deleted records, ordinary hidden records, hidden catalog assignments, inactive catalog records, unresolved catalog relationships, and nameless records do not enter active stock/value/classification summaries. The explicit hidden-products maintenance view starts from the already sanitized inventory read model and does not make hidden stock operational. Missing sale price is distinct from a valid zero. Product value is base-unit quantity × sale price; category value sums those per-product values, reports priced versus missing-price membership, and keeps uncategorized value outside the category ranking. The purchase-warning threshold only prioritizes review and never claims a recommended order quantity.

Invoice dashboard windows are calendar-day windows in `Asia/Tehran` for today, 7 days, and 30 days. They aggregate immutable invoice `total_amount` snapshots only. Accepted invoices and the last accepted state of `cancel_pending` invoices count; cancelled, rejected, conflicted, Team-unknown, and draft records do not. Solo pending records appear only in a separate unconfirmed section. Invoice ID de-duplication prevents post/cancel replay evidence from being counted twice. A valid zero is displayed as zero, while no rows, an unavailable total, and incomplete local history are different states.

The report route requires current invoice capability and `invoices.view`. Purchase counts as well as amounts are redacted without purchase-price visibility, including the separate Solo-pending section; sale aggregation uses the corresponding sale visibility. Online history hydration is store-scoped and records a person/store-scoped complete-fetch timestamp. Without that marker the UI calls the result partial and never presents local Team cache as complete. The report does not describe invoice totals as collected cash or purchase/sale differences as realized profit. No report action mutates stock, movements, invoices, or the outbox.

Dashboard browser restoration uses one stable app-shell scroll element instead of remounting it per pathname. Router and explicit return-anchor keys include authenticated person and store, so back navigation cannot reuse another partition's position. Desktop and mobile production-preview coverage exercises both browser back and the in-app dashboard return.

### Persian presentation, contextual help, activity, and dates

TZ-V1-08 keeps transport and policy identifiers out of the primary customer message. Unknown server text is not echoed as trusted customer copy. Connection and synchronization surfaces explicitly distinguish local persistence, server acceptance, image-byte coverage, independent backup, and an outcome that is still unknown. It explains the Solo/Team acceptance boundary, invoice cancellation/output limitations, search/filter/bulk behavior, local versus server evidence, independent backup limits, image recovery, and unresolved outcomes without inventing commercial allocation or authority. ### Restore

`backupRestoreService.apply` treats a backup as untrusted input. It verifies integrity, supported/legacy shape, owner/store binding, business relationships, authority-field exclusion, operation types, and included media before touching live state. It captures the current actor/store projections, every queue state, preferences, reconciliation metadata, and available local image bytes in a durable browser-local checkpoint. The checkpoint is recovery evidence for this browser, not an independent external backup.

The recoverable state machine is `preparing -> media_staged -> database_committed -> review -> complete`. Imported media is written and verified at unique staging paths before the scoped Dexie merge transaction. That transaction unions imported records with the checkpoint and gives the pre-restore record precedence for the same entity ID, so a newer edit or a local-only record absent from the backup remains in the live projection as well as the checkpoint. Snapshot absence is not a deletion instruction. A restart at `media_staged` aborts safely and removes staging because live IndexedDB was not changed. After `database_committed`, a per-file journal copies and verifies staged bytes to live paths and resumes after interruption; cleanup follows the persisted copy marker. Missing source media remains visibly unavailable.

Restore requires browser Web Locks and acquires the backup-writer, outbox-sync, and actor-local-mutation locks across checkpoint, staging, and commit. The bounded maintenance marker gives immediate same-account feedback, but is not the concurrency authority; if it expires, the Web Lock still excludes sync and mutation writers. A browser without Web Locks fails before checkpoint or mutation instead of using the expiring local-storage writer lease. Closing a real Chromium tab during a deliberately held media-stage write was verified to release the lock and abort the persisted `preparing` session on reopen. An operating-system/browser-process kill and a real post-commit tab termination remain unverified.

The current outbox is never deleted by restore. Snapshot records and backup operations become separate persistent review evidence. Never-attempted snapshot/new recovery changes receive a new operation id only after explicit approval and pass current access/permission and base-version checks. Attempted or uncertain operations retain their original operation id and exact semantic payload so the existing idempotent server replay can return a prior result without duplicating an effect. Terminal and unknown additive outcomes cannot be guessed; they remain discardable/exportable evidence. Review-item-to-operation mapping is atomic and idempotent, and resume refuses to complete while any decision or queued result remains unresolved. Discard can remove only a never-attempted pending recovery operation and never claims to cancel a possible server effect.

Legacy backup schemas 1–4 remain readable when their data is safe and unambiguous. The envelope SHA-256 value is an integrity checksum carried by the file, not a keyed signature or proof that imported identity claims are authentic. Imported cursors, success flags, authority, and absence-as-delete are not trusted. Restore remains owner/store-bound, offline local restore is labelled pending reconciliation, and submission still goes through the existing queue/sync acceptance path. Under 1D, new Team recovery submissions capture current policy and original uncertain evidence retains its historical context. This does not implement server disaster recovery, clean-device media hydration, or device-loss protection.

### Store-ownership migration and compatibility

Alembic `20261101_0009` expands `stores` with the authoritative business domain, backfills nullable operational `store_id` values first from the unique owner and then from an unambiguous membership, validates cross-store references, and only then makes ownership columns non-null and replaces owner-user uniqueness/indexes. It preserves primary keys, quantities, prices, category/transaction history, sync fingerprints, operation IDs, and cursors.

The migration deliberately raises `STORE_OWNERSHIP_PREFLIGHT:<table>:<reason>` for unresolved rows, cross-store references, or duplicate store/catalog, category, label, or actor-operation keys. The diagnostic includes the total and up to 20 affected record/group identifiers. PostgreSQL transactional DDL rolls the failed revision back to `0008`; operators must export and resolve the identified rows and retry. The migration does not select a winner, sum quantities, delete records, or rewrite operation semantics. A request committed under `20261101_0008` retains its fingerprint and recorded result and replays after upgrade without reapplying its mutation.

Schema `0009` is not rolling-compatible with pre-1B backend processes. The legacy process uses owner-user lookup/deduplication assumptions while `0009` enforces store/actor keys, so migration requires a controlled backend replacement: stop old workers, back up and preflight, apply `0009`, verify the Alembic head, then start only 1B-or-newer workers. The repository contains manual Alembic/start instructions but no automated production deployment or rollback workflow.

The local database already partitions projections, cursors, and outbox entries by actor and store. No Dexie version or backup format changed in 1B; schema-v2 backup store binding and legacy compatibility remain as before. Restore review behavior is intentionally unchanged and remains a 1C risk.

## TZ-V1-03 signup and profile-completion map

Public signup accepts username, required Iranian mobile, and password. Password confirmation remains entirely in the browser, while the server transaction creates the `User`, owner `Store`, owner `StoreMembership`, starter roles, and first `UserSession` together. Username and canonical-phone uniqueness are authoritative in the database; a concurrent loser rolls back and receives the corresponding controlled conflict rather than leaving a partial workspace. Supported `09…`, `+989…`, and `00989…` forms and Persian/Arabic-Indic/Latin digits converge to `09xxxxxxxxx`. The phone is not verified and does not alter username-based login. The initial plan/mode path remains Free/Solo and does not create a commercial grant.

Alembic `20261103_0012` makes only user first/last names nullable. Existing values, store IDs, membership/role data, plan/mode, operational data, sync history, fingerprints, and grants are unchanged. Minimal accounts use the username as the initial store display fallback. Downgrade has an explicit incomplete-profile preflight instead of inventing names.

Alembic `20261104_0014` preflights every non-null legacy phone at `0013`, reports only counts and sampled user IDs for malformed values or post-normalization duplicate groups, and refuses to choose a winner. After explicit remediation it canonicalizes valid values and installs `uq_users_phone_canonical`; null legacy/personnel values remain supported. Profile writes use the same normalization and database conflict mapping, including unchanged self-saves.

The reminder is derived from the authenticated `User` snapshot, not persisted as authority or a cross-account dismissal. It is emitted only for the active store owner when any deferred profile field is blank, uses informational severity, and routes to `/setting/profile`. Reload/viewing produces the same single derived item; the successful profile mutation updates the person/store-bound query snapshot and removes it. Store personnel and the isolated system-administrator workspace are excluded.

Production-preview coverage uses mocked APIs and therefore establishes responsive form/notification behavior, not live network or database behavior. Real PostgreSQL coverage establishes nullable migration state, transaction rollback, and one-winner concurrent signup. Browser/process loss at the exact response boundary remains represented by the invariant that credentials are stored only after a successful response; it was not tested by killing a real browser process.
